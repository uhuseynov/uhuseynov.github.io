Introduction#

WHAT ARE LOGS? AND WHAT ARE THEIR ESSENTIAL ROLES IN CYBERSECURITY?#

Logs are records of events and activities generated by systems, applications, and network devices during their operation. They are used to monitor system behavior, troubleshoot errors, and detect security incidents by providing visibility into what happened, when it happened, and where it occurred. In cybersecurity, logs are essential for incident response, forensic analysis, and compliance auditing.

Types of Logs#

Overview of common log types used in monitoring and security investigations.

Below are some of the most common and widely used log types in monitoring and security investigations.

System Logs capture operating system and hardware events such as boot processes, crashes, and system errors. They are commonly used to diagnose OS-level failures and performance issues.

Security Logs record authentication, authorization, and policy enforcement activities across the system. They play a critical role in detecting suspicious behavior and investigating security incidents. In many cases, they provide the first indicators of compromise.

Application Logs track events generated by applications, including user actions, errors, and configuration changes.

Audit Logs provide detailed visibility into system changes and user activities. They are essential for compliance, accountability, and forensic investigations. These logs help organizations prove what happened and who was responsible.

Network logs monitor incoming and outgoing traffic across network devices.

Access logs record who accessed specific resources and when the access occurred. They are useful for identifying unauthorized access and tracking resource usage.

Windows Event Logs Analysis#

Unlike other log files, Windows OS provides a utility called Event Viewer, which offers a graphical interface to view, search, and analyze logs. So, let’s explore Windows Event Viewer.

Overview of Windows Event Viewer and its role in log analysis.

Event Viewer groups log files into different categories, each containing related events. By selecting a category, we can use various built-in tools to filter and analyze the data.

From here, I started exploring Event Viewer in more detail ..

When I open Event Viewer, the first thing I usually look at is the list of log categories on the left side, such as System, Security, and Application. Clicking on any of these immediately shows the related events in the middle panel, where I can scroll through entries and check details like timestamps and event IDs. On the right side, I use the available options to filter, search, and narrow down the logs, which makes it much easier to focus on the events I actually care about during analysis.

When we double-click one of these logs, we see its contents:

This is how a Windows event log looks. It has different fields. The main fields I focused on are listed below:

  • Description: This field has a detailed information of the activity.
  • Log Name: The Log Name indicates the log file name.
  • Logged: This field indicates the time of the activity.
  • Event ID: Event IDs are unique identifiers for a specific activity.

Numerous event IDs are available in Windows Event logs. We can use these event IDs to search for any specific activity. I have mentioned some important Event IDs below:

4726 – A user account was deleted

4624 – A user account successfully logged in

4722 – A user account was enabled

4634 – A user account successfully logged off

4725 – A user account was disabled

4625 – A user account failed to log in

4720 – A user account was created

4724 – An attempt was made to reset an account’s password

One of the easiest ways to simplify the analysis is by filtering event IDs:

Below, I describe all my actions step by step.

First, I went to the Actions panel on the right side of Event Viewer and clicked Filter Current Log… (1). This helps avoid scrolling through hundreds of events and allows me to focus only on what I’m actually looking for.

Next, in the filter window, I used the Event ID field and entered 4624 (2). I left everything else as default since my goal was simply to display successful logon events.

After clicking OK, Event Viewer refreshed the list and showed only Event ID 4624 entries (3). From there, I could easily review timestamps, usernames, and other details without the noise of unrelated logs.

Web Server Access Logs Analysis#

While exploring how websites actually handle user activity, I started paying more attention to web server access logs. Every interaction with a website—loading a page, submitting a form, or logging in—results in a request that the server records. These logs quietly capture what users are doing in the background, often without anyone noticing.

On systems running Apache, these requests are typically stored in a file like:

root@kali$ /var/log/apache2/access.log

This file becomes especially useful when something feels off, such as unexpected errors, repeated requests, or suspicious access patterns.

Making Sense of a Log Line#

At first glance, access logs look messy and hard to read. But once I got used to the structure, each line started to tell a small story. A single entry usually answers a few key questions: who made the request, what they tried to access, when it happened, and how the server responded.

Here’s an example I worked with:

root@kali$ cat access.log
172.16.0.1 - - [24/Jan/2026:22:16:44] "GET /products HTTP/1.1" 404 "-" "Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/58.0.3029.110 Safari/537.36"
10.0.0.1 - - [24/Jan/2026:22:15:44] "GET / HTTP/1.1" 404 "-" "Mozilla/5.0 (Macintosh; Intel Mac OS X 10_12_3) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/58.0.3029.110 Safari/537.36"
192.168.1.1 - - [24/Jan/2026:22:14:44] "GET /about HTTP/1.1" 500 "-" "Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/58.0.3029.110 Safari/537.36"

From this alone, I can tell that a user tried to access a /products page, but the server responded with a 404, meaning the resource wasn’t found. Even without extra tools, this already gives useful context.

Exploring Logs from the Terminal#

When I start analyzing logs, I usually begin by simply opening the file:

root@kali$ cat access.log

This is fine for quick checks, but it doesn’t scale well once the log file grows. Scrolling through hundreds of lines manually isn’t practical, so I quickly moved on to more efficient approaches.

Narrowing Down Results Instead of Reading Everything

Rather than reading logs line by line, I focus on filtering what matters. For example, if I want to see all activity from a specific IP address, I use:

root@kali$ grep "192.168.1.1" access.log
192.168.1.1 - - [24/Jan/2026:22:14:44] "GET /about HTTP/1.1" 500 "-" "Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/58.0.3029.110 Safari/537.36"
192.168.1.1 - - [24/Jan/2026:22:11:44] "GET /products HTTP/1.1" 404 "-" "Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/58.0.3029.110 Safari/537.36"
192.168.1.1 - - [24/Jan/2026:22:04:44] "GET /about HTTP/1.1" 200 "-" "Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/58.0.3029.110 Safari/537.36"

This immediately reduces noise and makes patterns easier to spot, especially when investigating repeated requests or unexpected behavior.

Handling Logs Split Across Multiple Files#

Web servers usually rotate logs, meaning activity is spread across multiple files. When I need a broader view across different periods, I combine them into a single file:

root@kali$ cat access1.log access2.log > combined_access.log

This makes analysis simpler and avoids jumping back and forth between files.

Reading Logs Without Overwhelming the Terminal#

For larger logs, I prefer using:

root@kali$ less access.log
172.16.0.1 - - [24/Jan/2026:22:12:44] "GET /products HTTP/1.1" 404 "-" "Mozilla/5.0 (Windows NT 6.1; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/58.0.3029.110 Safari/537.36"
10.0.0.1 - - [24/Jan/2026:22:08:44] "GET /about HTTP/1.1" 404 "-" "Mozilla/5.0 (Windows NT 6.1; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/58.0.3029.110 Safari/537.36"
192.168.1.1 - - [24/Jan/2026:22:06:44] "GET /about HTTP/1.1" 200 "-" "Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/58.0.3029.110 Safari/537.36"

What I like about this approach is the ability to move through logs gradually and search within the file when needed. It feels much more controlled compared to dumping everything to the screen at once.

Why This Approach Matters to Me#

Going through raw access logs manually helped me understand what normal web traffic looks like. Once that baseline is clear, unusual patterns stand out much faster. This kind of hands-on analysis builds intuition that automated tools alone can’t provide.

For me, learning log analysis this way makes every higher-level security concept easier to understand later on.

Conclusion#

Logs and monitoring are not just technical concepts; they are the foundation of how defenders actually understand what is happening inside a system. Without logs, incidents become guesses, timelines fall apart, and attackers leave behind unanswered questions. Every login, request, error, or configuration change tells a small part of a much bigger story.

While learning different log types and tools like Windows Event Viewer or web server access logs, I realized that effective monitoring is less about collecting everything and more about knowing what to look for and when. Simple techniques like filtering by event IDs or searching specific patterns can quickly turn overwhelming data into useful insights.

This topic is a core part of defensive security and SOC work, and it’s something I’ll continue to practice and improve. As I move forward, I plan to dive deeper into real-world detection scenarios, correlation between logs, and how monitoring helps identify attacks before they cause real damage.

This blog is mainly a way for me to organize what I’m learning and track my progress. If it also helps someone else understand logs and monitoring a bit more clearly, that’s a bonus.
